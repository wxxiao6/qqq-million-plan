# 用户系统后续扩展计划

更新日期：2026-11-04。以下为尚未实现的多用户扩展要求，不是当前能力或本轮交付范围。当前单账号实现见 [用户系统设计](user-system-design.md)，旧部署记录见 [历史实施记录](history/user-system-2026-10-30.md)。

## 开放第二个账号之前

1. 每个业务读写方法接收可信用户上下文；所有 SELECT、UPDATE、DELETE、关联、聚合和判重显式约束 `user_id`，不得信任表单中的用户 ID。
2. 为持仓、计划、执行和快照建立完整归属及约束；快照唯一键改为用户与日期，个人偏好与共享配置分离。
3. 拒绝跨用户计划关联；不存在和越权记录统一返回未找到。后台任务按归属处理，任务凭证不能作为个人登录凭证。
4. 明确共享净值、导入、行情刷新等写权限；普通用户不能任意覆盖影响所有人的数据。需要个人净值覆盖时采用独立数据模型。
5. 保留 SQLite 事务和 D1 批次原子性；并发、重试、失败不得造成重复记账、重复累计或跨用户快照污染。

## 迁移和验收

- 先取得历史数据所有者的明确映射并完整备份；在隔离 SQLite 和真实 D1 中演练，核对行数、金额、空归属、孤儿关联和唯一约束。
- 维护窗口暂停写入及后台任务，完成迁移与核对后协调发布；失败时保留新增数据并按恢复方案处理，不能直接覆盖上线后的增量。
- 验证匿名、失效、已撤销会话及跨用户 ID 操作均被拒；检查共享缓存、Cookie、来源检查和机器认证边界。
- 覆盖两种后端的读取、写入、导入、确认、定投和快照，并在真实 D1 验证约束、批次失败与并发行为。
- 邀请、注册、找回密码及第三方身份服务需另行设计，在上述隔离完成前保持单管理员限制。

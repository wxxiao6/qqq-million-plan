# 用户系统实施计划与技术方案

日期：2026-10-30  
状态：首版代码已实现并完成隔离 SQLite 本地试用；生产 Worker 与 D1 迁移已部署，但生产管理员账号尚未初始化。参见[用户系统设计](user-system-design.md)与[实施记录](user-system-plan.md)。

## 1. 目标与已知约束

- 持仓、待确认申购、定投计划及执行记录按用户隔离；用户仅能读写自己的数据。定投仅记账，不发起真实交易。
- 同时支持本地 SQLite 和 Cloudflare D1；保留现有基金、渠道、状态和扣款规则。
- 基金目录、行情和公开净值作为共享数据；组合市值、计划、持仓和个人设置归用户所有。
- 原站点级 owner Basic Auth 已从应用和 Worker 配置移除；仓库中没有遗留的 Basic Auth 认证入口。本人账号密码登录、会话和持仓入口保护已经实现；定投管理保持匿名可用。当前严格限定为一个管理员账号；数据查询尚未全部改为多用户 SQL 隔离，因此不得创建第二个账号或将系统作为多用户服务开放。
- 第一版限定本人单账号，使用账号密码登录；关闭公开注册。共享资产、自助删除和导出不纳入本期。

## 2. 推荐架构

采用共享数据库 + 每条业务记录的 `user_id`。Web 请求先由服务端验证会话。首版仅本人使用，管理员初始化时认领全部历史记录，触发器为后续账本写入添加管理员 ID。若未来扩展多人，仍需先将所有业务 SQL 改为显式用户上下文和查询隔离。定时任务使用独立的系统执行入口，枚举计划后显式传入归属，绝不从请求参数取得信任身份。

```text
浏览器 -> 页面 / Server Action / API -> 认证与 requireUser() -> 用户上下文
                                                   |                  |
                                          个人数据服务 -> SQLite / D1，SQL 约束 user_id
调度器 / 机器任务 -> 独立任务鉴权 -> 系统任务 -> 按用户或计划处理 -> SQLite / D1
                                          共享目录 / 净值：明确只读或受控写入
```

### 2.1 认证和会话

已实现首版仅本人登录，当前采用服务端 PBKDF2 密码哈希和随机不透明会话令牌：会话令牌只以 SHA-256 摘要写库；首个账号由一次性初始化口令创建，之后不可注册。后续若开放多人或找回密码，再迁移至成熟身份服务。

- `users.id` 为应用生成的稳定标识；首个账号为管理员，邮箱唯一并用于登录。
- 建议封装 `getCurrentUser(): Promise<User | null>` 和 `requireUser(): Promise<UserContext>`；后者验证会话、用户状态及有效期。页面无会话时跳转登录；Action/API 返回明确的未认证结果。目标记录不存在与越权使用相同的未找到结果。
- 会话 Cookie 使用 `HttpOnly`、`Secure`（HTTPS 环境）、适当的 `SameSite` 与有效期；实现退出撤销、会话到期和禁用账号的失效策略。状态变更保持来源/CSRF 防护；登录限流和恢复策略依据选型落地。
- 登录回调校验目标地址，阻止开放重定向；个人响应 `private, no-store`，缓存键不得跨用户复用。用户服务不可用或验证失败时拒绝个人数据访问；日志不记录令牌及资产详情。
- 用户只能通过经过认证的服务端上下文取得 `userId`；任何表单、URL、客户端 JSON 中的同名字段不能作为授权依据。任务令牌不能作为用户凭证。

### 2.2 数据模型与查询约束

以下区分当前首版实现和未来多人化目标。044 号迁移已经为账本表增加可空 `user_id`、索引与单管理员自动归属触发器；由于 D1 与 SQLite 的现有约束及查询尚未完成多用户改造，当前仅支持一位管理员。不能把目标设计表格理解为所有结构均已落地。

| 对象 | 改造 | 约束/索引 |
| --- | --- | --- |
| `users`、`user_identities` | 用户与外部身份映射 | 用户主键；身份 `(issuer, subject)` 唯一；用户状态与创建时间 |
| `positions` | 增加必填 `user_id` | 用户外键；按 `(user_id, id)`、常用筛选列和 `(user_id, dca_plan_id, execution_on)` 建索引 |
| `dca_plans` | 增加必填 `user_id` | 用户外键；按 `(user_id, id)`、状态和到期时间索引；原基金/账户/未结束重复规则前加用户维度 |
| 计划关联 | `positions.user_id` 与计划一致 | 评估 `dca_plans (user_id, id)` 唯一键及复合外键；手工持仓的 `dca_plan_id` 可为空；在两种数据库验证约束与迁移行为 |
| `portfolio_snapshots` | 为历史和新快照增加用户归属 | 从按日期唯一改为 `(user_id, as_of)`；所有聚合及 upsert 带用户 |
| `user_settings` | 保存个人偏好 | `(user_id, key)` 唯一；迁移 `holdings.enabledTypes`。`app_kv` 的共享配置和并发保护键保留原用途 |
| 目录、额度、`nav_snapshots` | 按共享数据处理 | 非个人资产；盘点读取与写入入口，并单独定义共享数据写权限 |

用户仓储方法必须要求 `UserContext`，例如 `listPositions(ctx)`、`updatePosition(ctx, id, input)`、`getDcaBoard(ctx)`；SQLite/D1 两种实现都必须遵守。新建记录由服务端填充归属；`SELECT`、`UPDATE`、`DELETE`、子查询、关联、重复检查及快照聚合均带 `user_id`。更新以受影响行数判定成功；外部传入 ID 即使有效但不属于当前用户也不可操作。跨用户计划关联在数据库约束和业务写入层双重校验。

`positions` 与 `dca_plans` 的现有主键是全局 ID，不能因此省略用户过滤；避免先按 ID 读出全部数据再在应用层过滤。公共行情查询不应把其他用户的持仓/计划信息返回给浏览器。

### 2.3 页面、操作与后台任务

| 入口 / 文件 | 具体实施 |
| --- | --- |
| [定投页面](../src/app/dca/page.tsx) | 保持匿名读取和 Server Actions；个人结果不进入共享缓存 |
| 持仓页面 | 首先 `requireUser()`；将上下文传给数据读取及页面触发的对账；个人结果不进入共享缓存 |
| [持仓 Actions](../src/server/ledger/actions.ts)、[持仓服务](../src/server/holdings/actions.ts) | 每个 Action 单独认证；改造持仓新增/修改/删除、待确认、导入、设置和快照，不能只在页面入口检查 |
| [定投 Actions](../src/server/dca/actions.ts)、本地及 D1 服务 | 计划创建、编辑、暂停、恢复、结束、删除、执行和修正都带用户上下文；关联更新和重复检查同样限定用户 |
| [D1 持仓读取](../src/server/holdings/read-d1.ts)、定投读取和汇总 | 数据库侧过滤用户；明细、收益、日历、汇总、重复提示及关联 JOIN 一起改造 |
| [定投对账](../src/server/ledger/reconcile-d1.ts)、本地 `recent-pending.ts` | 区分 `reconcileForUser(ctx)` 和仅后台可调用的批处理入口；生成记录时继承计划归属，原子更新累计、进度和快照 |
| [计划任务](../src/server/jobs/scheduled-dca.ts)、[Worker](../worker.mjs)、`/api/jobs/*` | 保留机器认证边界；按用户/计划分批，失败可重试，记录脱敏结果；页面和定时任务并发保证幂等 |
| [净值与快照](../src/server/market/nav-d1.ts)、[快照写入](../src/server/ledger/snapshot-write-d1.ts) | 共享净值可批量更新；自动确认涉及个人记录时保留归属并分别重算受影响用户的快照；个人写入只更新该用户快照 |
| [导入](../src/server/ledger/import-d1.ts)及 CSV 操作 | 只能导入当前用户并在用户范围判重；明确共享净值导入的写权限 |

**共享净值写权限是实施前必须确定的安全边界**：现有 `saveNav`、`importNavCsv` 会修改全局净值，影响其他用户的估值。推荐第一版仅允许受信任的后台任务或明确授权的运营身份修改共享净值；普通用户不能调用这些写入口。若需个人手工净值，应另建用户私有覆盖数据及明确优先级，不能改写全局值。行情刷新、额度上报和其他全局修改入口也要逐一盘点授权。不能仅隐藏按钮。

### 2.4 幂等和原子性

沿用现有执行日期和状态语义，先检查历史记录和手工修正规则，再确定适用的幂等键或部分唯一约束；禁止未经核实地假定所有 `(plan_id, execution_on)` 唯一。页面与定时任务同时触发时，创建记录、更新计划累计与进度必须在同一 SQLite 事务或经真实 D1 验证的原子批次中完成。并发条件更新失败时重新读取或返回可重试结果，避免重复累计。快照的事务边界、净值批处理后的补算及失败重试需要分别验证。

## 4. 数据迁移和发布步骤

1. **迁移前核对**：确认每条历史数据的所有者及其已验证身份；禁止让第一个注册者自动认领。检查孤儿计划关联、重复执行、快照、用户偏好；记录每表行数、按状态数量、份额、成本、现金、计划累计及关联数。
2. **备份和演练**：对生产数据做可恢复备份，在独立 SQLite 和真实 D1 测试环境演练完整迁移、核对及恢复；确定 D1 批次或表重建的实际原子边界。使用明确映射回填，不在普通自动迁移中硬编码所有者。
3. **维护窗口**：暂停个人写入、计划对账、净值回写、导入及其他后台写入口；确认无在途任务。按确认的映射创建用户并回填，重建必要约束、索引和快照键；若存在无法归属或异常数据则中止开放。
4. **验收与恢复**：逐项比较迁移前后的行数、金额、计划关联、快照和设置；检查空归属及跨用户关联均为零。部署完整版本，验证用户隔离与机器任务，再恢复调度和写入。
5. **回滚**：出错时保持停写，恢复经演练的旧应用和数据库备份，复核后恢复服务。若上线后已有新写入，先停止写入并保存增量，明确重放或人工合并后再恢复；禁止直接用旧备份覆盖新增数据。数据库回滚不会随代码回滚自动完成。

## 5. 测试与验收矩阵

- **身份**：无会话、过期、已退出、已撤销、已禁用及身份服务异常均不能读取或修改个人资产；机器令牌不能登录；登录跳转及 Cookie、来源检查符合方案。
- **隔离**：匿名访问不能查看或修改持仓、待确认、计划及汇总；本人登录后页面和所有 Server Actions 正常。首账号完成后再次调用初始化接口会被拒绝。
- **一致性**：拒绝跨用户计划关联；页面和定时任务并发运行、重复运行、部分失败与重试后，无重复记账或重复累计；净值更新后的用户快照正确且互不覆盖。
- **共享数据**：普通用户直接调用手工净值及其他共享写入口被拒；可信后台权限单独测试；公共读取符合最终访问决策。
- **迁移**：空库、正常历史数据、孤儿/重复等异常副本均按预期处理；总数、金额、关联、快照和偏好可核对；失败和上线后增量恢复均经过演练。
- **运行环境**：SQLite 与 D1 运行同一组关键业务和隔离测试；真实 D1 环境验证迁移、约束、原子批次和并发。执行现有测试、lint 和构建，监控认证、迁移及任务失败，日志不含凭据或资产明细。
